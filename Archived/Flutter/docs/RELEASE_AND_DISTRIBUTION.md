# Flux News Release and Distribution

This document contains release, reproducibility, signing, F-Droid, and external policy context. Current external requirements must always be revalidated against primary/official sources before making release decisions.

## Release, F-Droid, And Signing

- Android has three real signing identities for the same package: Google Play App Signing, the developer/GitHub release key, and F-Droid's repository key. They are update-incompatible unless an installed app receives an APK signed by its existing key (or a supported signing lineage). Never assume package name equality is enough for an Android update.
- A direct comparison of the published ARM64 `2.1.1` GitHub and F-Droid APKs with `apksigcopier` failed. The actual differing payload files were `NativeAssetsManifest.json`, `libapp.so`, and `libdartjni.so`. The main cause was GitHub building all split ABIs together while F-Droid builds each record with one explicit `--target-platform`.
- `.github/workflows/build-and-release.yml` mirrors F-Droid: it uses the checked-in Flutter submodule, a workspace `PUB_CACHE`, applies the same no-Play Cronet preparation, and builds x86_64, armeabi-v7a, and arm64 separately with `--target-platform=android-x64`, `android-arm`, and `android-arm64`. It then additionally builds the universal GitHub APK. This setup produced confirmed reproducible split APKs for release `2.2.5`.
- GitHub Actions must restore the Git tag for the shallow Flutter submodule before running Flutter. The workflow resolves the semantic release tag from the checked-out submodule commit via `git ls-remote`, fetches only that tag, and verifies the commit/tag match. This avoids a second manually maintained Flutter version becoming stale after submodule updates. Without the tag, Flutter reports `0.0.0-unknown` and Pub rejects packages with a minimum Flutter SDK such as `workmanager`.
- GitHub release builds are copied to and built from `/home/vagrant/build/de.circle_dev.flux_news`, with `PUB_CACHE` inside that directory and `ios` removed from the copied tree, to match the absolute path and Android-only source layout used by F-Droid. This is required because Dart AOT output can embed source URIs such as `.dart_tool/flutter_build/dart_plugin_registrant.dart`; building from GitHub's default `/home/runner/work/...` path breaks byte-for-byte reproducibility.
- The published GitHub and F-Droid `2.2.4` split APKs were compared for all three ABIs. All 1,153 non-signature payload entries have matching names, order, and ZIP metadata; 1,152 are byte-identical. The only mismatch is exactly 20 bytes in each ABI's `libdartjni.so`: the GNU build ID in `.note.gnu.build-id`. Removing that section makes each GitHub/F-Droid library pair byte-identical. Therefore `2.2.4` is not strictly reproducible. `libdartjni.so` comes from the transitive `jni` package (currently `jni 1.0.0`, pulled by `cronet_http` and `path_provider_android`). For subsequent releases, `android/build.gradle` configures only the `jni` library subproject with `-DCMAKE_SHARED_LINKER_FLAGS=-Wl,--build-id=none`.
- Release `2.2.5` is strictly reproducible for all three split APKs. On 2026-07-27, pinned `apksigcopier 1.1.1 compare` completed with exit code `0`, without `--ignore-differences`, for GitHub versus F-Droid x86_64 (`2026072202`), armeabi-v7a (`2026072203`), and arm64-v8a (`2026072204`). Package name, version `2.2.5`, version codes, and ABI assignments also match. The developer signing-certificate SHA-256 is `fee5401bc9d59cf5a8a461ba9698c482e87ed8ffb9258786a3d01d0356ea2ebb`; the F-Droid certificate SHA-256 is `d8e5c241fc3ed7e8b1fdcfb237e4b2680e763e3c2c1412c91ff568d6c57eabd7`.
- ABI version codes add `+1` for x86_64, `+2` for armeabi-v7a, and `+3` for arm64-v8a to the base `pubspec.yaml` build number. Keep F-Droid metadata, release assets, and changelog filename selection aligned with this scheme.
- The base Android build number uses the fixed-width decimal form `YYYYMMDDNN` (date plus a two-digit sequence), which stays parseable by F-Droid's update tooling while remaining below Android's signed 32-bit version-code ceiling for the foreseeable project lifetime. Reserve the next three integers for the ABI outputs and avoid choosing a later base code that overlaps a previously published `base+1` through `base+3`. Store changelogs under the actual ABI version codes; the GitHub release body currently uses the x86_64 (`base+1`) changelog.
- With reproducibility confirmed for `2.2.5`, F-Droid can publish both developer-signed and F-Droid-signed variants. Existing F-Droid users can remain on the F-Droid key while new/external installs can use the registered developer key.
- The GitHub tag workflow extracts the developer signatures from all three ABI APKs with pinned `apksigcopier 1.1.1`, stores them in F-Droid's `metadata/de.circle_dev.flux_news/signatures/<versionCode>/` layout, and attaches `fdroid-signatures-v<version>.tar.gz` to the GitHub release. Every v2/v3-only signature directory must contain `APKSigningBlock`, `APKSigningBlockOffset`, and `signer-certificate.der`; current fdroidserver ignores the developer signature graft when the DER certificate is missing.
- `.github/scripts/extract_signer_certificate.py` verifies each signed release APK with Android `apksigner`, extracts all reported PEM signer certificates, selects only the certificate matching the pinned developer SHA-256 fingerprint, and writes its DER representation. The release workflow includes it in future archives. The F-Droid submission workflow also derives and overwrites it from each downloaded ABI APK so releases created before this fix, including `2.2.6`, can be submitted safely.
- After the GitHub release is created, `.github/workflows/build-and-release.yml` calls `.github/workflows/submit-fdroid-signatures.yml` as a dependent reusable workflow for the same release tag. The release workflow waits for the F-Droid submission and reports a failure if that job fails. There is no scheduled retry; `workflow_dispatch` remains available for an explicit retry.
- F-Droid's built-in `AutoUpdateMode` cannot safely remain enabled for dual publication because each release needs new extracted developer-signature files and fdroidserver does not yet retrieve them automatically (tracked upstream as fdroidserver issue `#1013`). Flux News therefore uses `AutoUpdateMode: None` with `UpdateCheckMode: Tags`, matching F-Droid maintainer guidance and the established Feeder dual-signature process. Release automation remains automatic through the GitHub workflow rather than the F-Droid checkupdates bot.
- The Android build uses the legacy Kotlin Gradle Plugin `2.3.20` with AGP `9.1.1`, Gradle `9.3.1`, and Java 17. `android.builtInKotlin=false` and `android.newDsl=false` intentionally remain temporary compatibility opt-outs because active dependencies such as `flutter_carplay` and `cronet_http` still apply `kotlin-android`; Flux News does not use a partial app-module Built-in Kotlin migration. Remove these opt-outs and the explicit KGP application only after the complete Android plugin graph supports AGP Built-in Kotlin and the legacy ABI variant logic has moved to the new DSL.
- The submission workflow creates one combined fdroiddata MR per release: it copies the latest enabled x86_64, armeabi-v7a, and arm64-v8a build recipes, updates version name, `+1/+2/+3` version codes, and full release commit SHA, updates `CurrentVersion`/`CurrentVersionCode`, keeps both `AllowedAPKSigningKeys`, and adds the extracted signatures. If all three release build entries already exist (such as the initial `2.2.5` migration), it validates and reuses them rather than duplicating them. Partial releases, mismatched commits/ABIs, unexpected `VercodeOperation`, disabled templates, or tag/pubspec mismatches fail the workflow for manual review.
- `.github/scripts/prepare_fdroid_metadata.py` performs a minimal text-preserving metadata edit so the large fdroiddata YAML remains reviewable. Its focused tests cover new releases, existing build entries, partial releases, disabled templates, and idempotency against the actual Flux News metadata layout.
- A green fdroiddata MR pipeline alone does not prove that developer signature grafting ran. The build log must process all three signature directories without verification failures, and build artifacts must include developer-signed APKs suffixed with the short developer fingerprint (currently `_fee5401.apk`) in addition to the regular F-Droid-signed APKs.
- The signature-submission workflow must not clone `fdroiddata` with `--depth=1`: GitLab rejects a new fork branch based on that checkout with `shallow update not allowed`. It uses a non-shallow blobless partial clone plus sparse checkout for the Flux News metadata and signature paths, retaining complete commit ancestry without downloading the full repository contents.
- The first Flux News dual-signature MR exposed a `fdroiddata` CI edge case: `tools/find-changed-builds.py` recognizes changed signature files only after it unconditionally reverse-applies the app metadata diff, so a signature-only MR fails with `No valid patches in input`. Combined metadata-and-signature MRs avoid this failure. The initial metadata setup adds both independently verified keys: developer/GitHub `fee5401bc9d59cf5a8a461ba9698c482e87ed8ffb9258786a3d01d0356ea2ebb` and legacy F-Droid `d8e5c241fc3ed7e8b1fdcfb237e4b2680e763e3c2c1412c91ff568d6c57eabd7`.
- F-Droid submission no longer uses a repository state variable or a separate dispatch token. An existing workflow-owned release branch is updated with `--force-with-lease`, preserving its open MR. Failed submissions are retried manually with the release tag after the cause is fixed.
- Required GitHub repository configuration for this automation: variable `FDROID_GITLAB_FORK` with value `namespace/fdroiddata` and GitLab secret `FDROID_GITLAB_TOKEN` with `write_repository` access to the fork. The obsolete `ENABLE_FDROID_SIGNATURE_SUBMISSION` variable and `FDROID_WORKFLOW_CONTROL_TOKEN` secret can be removed from the repository settings.
- Google Android Developer Verification is an evolving external policy and must be rechecked online before release decisions. As of 2026-07-27, all three independently verified distribution certificates are registered with Google for Flux News: developer/GitHub `fee5401bc9d59cf5a8a461ba9698c482e87ed8ffb9258786a3d01d0356ea2ebb`, F-Droid `d8e5c241fc3ed7e8b1fdcfb237e4b2680e763e3c2c1412c91ff568d6c57eabd7`, and Google Play App Signing `f1a27813cdb8ebbf47fd851c3596be5d23af82e14ee005dfb5956d680ddebbae`. The Play certificate was verified directly with `apksigner` against the Play-generated APK `202605291.apk` (version `2.1.0`, version code `202605291`). Its separate Google Source Stamp certificate is metadata and is not an app signing identity. Dual F-Droid publication helps future developer-signed installs but does not itself migrate existing F-Droid-signed installations.

# Flux News Product Backlog

These entries describe ideas, favored directions, or implementation-ready concepts. They are not evidence that a feature is currently implemented. Always verify the repository state before acting on them.

## Product Feature Ideas And Existing Bulk Actions

- Implementation-readiness differs by idea: the shared-URL import has a repository-specific technical design and can be implemented after revalidating current APIs/plugins; full Miniflux feed management and the podcast queue currently have agreed product scope and architectural constraints but still require endpoint/data-model/UI integration analysis; the remaining lower-priority ideas are backlog concepts only and must be analyzed before implementation.
- Do not propose generic news-card multi-selection as an unimplemented replacement for bulk read actions without rechecking the AppBar menus. Both AppBar implementations (`lib/ui/flux_news_body.dart` and `lib/ui/sliver_glass_app_bar.dart`) already expose one context-sensitive `PopupMenuButton` action that marks all unread items in the current scope as read. Its label and database scope adapt to All News, Bookmarks, the selected category, or the selected feed. `showDeleteAllDialog()` collects the affected IDs before the local update, optionally pushes them to Miniflux immediately, updates the widget snapshot, and advances/reloads the current view. Per-item swipe actions and optional mark-as-read-on-scrollover already cover efficient individual and traversal-based handling. Generic card-by-card multi-selection is therefore not currently prioritized.
- Full Miniflux feed management remains a possible larger feature. Existing `FeedOnboarding` creates only curated feed suggestions, while the current feed settings screen primarily stores Flux News-specific local display behavior. Website-level feed management would add arbitrary URL discovery and selection, feed create/edit/move/refresh/disable/delete, parsing-error and last-check diagnostics, category create/edit/delete/refresh/hide-globally, OPML import/export, and version-gated advanced Miniflux fields such as crawler/scraper/rewrite/filter rules, authentication/cookies, cache/TLS/HTTP2/proxy behavior, and media/global-visibility options. Keep Miniflux-owned settings visually separate from Flux News-only feed overrides. Miniflux remains the source of truth.
- A persistent podcast Up Next queue is a favored feature idea. It should support downloaded episodes through local files and optionally non-downloaded episodes through streaming or an explicit download-before-play policy. Automatically generated queues should sort episodes globally by publication date (oldest/newest selectable), not group them by feed; choosing one feed is an explicit filter. Manual Play Next/Add to End and reordering should override the generated order. Persist attachment/news IDs, order, and current index, and use a queue snapshot so a sync cannot unexpectedly reorder active playback. CarPlay/Android Auto may default to downloaded-only content for reliability.
- Importing a shared URL into Miniflux is a favored feature idea for Miniflux >= 2.2.16. The endpoint requires an existing feed ID. The import dialog should try to match the URL host to an existing feed, preselect that feed, allow a different feed to be chosen, and optionally remember a fallback/default feed for unmatched URLs. It may also expose unread/bookmark and fetch-full-content choices; after import, Miniflux's fetch-content endpoint can populate article content. The feature must be hidden or explained for older supported Miniflux versions.
- The URL-import API flow is explicitly two-stage. Create the entry with `POST /v1/feeds/{feedID}/entries/import`; the URL is required, status defaults to read when omitted, title can default to the URL, and omitted content remains empty. When the user requests full content, follow the successful import with `GET /v1/entries/{entryID}/fetch-content?update_content=true`; Miniflux does not automatically fetch the article body after the import call. Afterwards run the normal Flux News sync/reload path so database metadata, list ordering, counts, and widgets remain consistent.
- The preferred share architecture keeps Miniflux credentials out of Android intent handlers and the iOS share extension. Native code should capture only the shared URL/title, persist one pending import, and open/activate Flux News. Flutter then waits for successful configuration/database initialization, presents the feed-selection dialog, performs the authenticated API calls through `lib/miniflux/miniflux_http_client.dart`, and consumes the pending payload only after it has been handed to the dialog. Handle cold start, warm `onNewIntent`/scene URL delivery, cancellation, duplicate delivery, malformed/non-HTTP URLs, API/version errors, and process death.
- Android can extend the existing `MainActivity.kt` pending-action bridge and `singleTop`/`onNewIntent` handling with an `ACTION_SEND` `text/plain` intent filter. iOS needs a Share Extension using the existing App Group `group.dev.kevincfechtel.fluxNews` plus activation of the host app. The current Runner uses a custom `SceneDelegate`, a shared headless-capable Flutter engine, a `fluxnews://` URL scheme, and a separate CarPlay scene configuration; preserve those lifecycle paths and do not replace the scene delegate without verifying widget actions, CarPlay, background sync, and cold/warm startup behavior.
- `receive_sharing_intent` is not currently a project dependency. It is a possible implementation aid, but its iOS Share Extension/UIScene integration is not assumed to be drop-in for this custom lifecycle. Prefer the smallest robust native bridge unless current plugin behavior is reverified against the installed Flutter/iOS setup. Add focused tests for request payloads and version gating, host-to-feed matching, pending-share consume-once behavior, initialization deferral, and import/fetch-content failure paths; manually test Android and iOS cold/warm sharing and CarPlay/Android Auto regressions.
- Other lower-priority ideas: offline article images with explicit storage/network policies; best-effort per-feed/category local notifications or digests (limited by OS background scheduling without a push service); article text-to-speech integrated with the existing audio focus and media controls; Siri/App Intents and Android shortcuts for sync/open-bookmarks/resume-playback; an in-app sync diagnostics/status view; and, as a high-complexity future option, multiple Miniflux accounts with isolated databases, credentials, settings, widgets, and audio state.

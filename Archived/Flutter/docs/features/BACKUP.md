# Flux News Backup and Restore

Detailed context for Android Auto Backup, manual settings backups, encryption, restore behavior, and local-data deletion scopes.

## Android Settings Backup

- Android Auto Backup is enabled in the manifest, but Flux News only writes the included file after explicit user opt-in via the dedicated Android backup switch in the settings list. The backup rules are scoped by `android/app/src/main/res/xml/backup_rules.xml` and `android/app/src/main/res/xml/data_extraction_rules.xml` to a single backup file: `files/android_auto_backup/flux_news_auto_backup.fnbak`.
- `flutter_secure_storage` data, SQLite databases, SharedPreferences, cache, and all other app data are intentionally not part of Android Auto Backup. This avoids the known Secure Storage/Keystore restore problems.
- Backup implementation lives in `lib/functions/settings_backup_service.dart`.
- Manual settings export writes a `.fnbak` file instead of the old plain ZIP. The export dialog offers an explicit "Create backup without encryption" switch for convenience; otherwise a non-empty password creates an encrypted backup. Encrypted payloads wrap the existing ZIP/JSON backup format, and legacy unencrypted ZIP restore remains supported.
- Encryption uses `cryptography`: Argon2id for password-based key derivation and AES-256-GCM for authenticated encryption.
- The settings list includes an "Include app settings in Android backup" switch on Android, disabled by default. If disabled, `refreshAndroidAutoBackupIfPossible()` deletes any local auto-backup file and writes nothing. If enabled, Android may back up the generated file according to the system backup schedule.
- When the Android backup switch is enabled, the settings list shows a status tile based on the local `flux_news_auto_backup.fnbak` file. It reports whether the local file exists and uses the file modification timestamp as the last-change time.
- Enabling the Android backup switch opens the same password/encryption prompt used by manual export. For encrypted Android auto-backups, the password is stored locally in `flutter_secure_storage` so future refreshes stay encrypted. For unencrypted Android auto-backups, the local password is deleted. The password and the auto-restore handled fingerprint are explicitly removed from backup payloads, so they are not restored through Android Auto Backup.
- On Android app startup/config load, the app refreshes the auto-backup file only if Android backup inclusion is enabled. If a local backup password exists, the file is encrypted; otherwise it is written unencrypted. Restoring an Android auto-backup is not prompted automatically at startup; users must use the Android Welcome screen's manual "Check Android backup" button.
- The Android auto-backup restore path logs detection, fingerprint handling, password-required parsing, password cancellation/invalid cases, and restore counts through `SettingsBackupService`. The Android Welcome screen button ignores the handled fingerprint so users can retry after dismissing the restore prompt.
- Feed metadata remains owned by Miniflux and is no longer exported from the DB in new settings backups. Local per-feed app options are mirrored into Secure Storage under `feedSettingsOverrides`, keyed by `feedID`. Existing DB values are migrated into this key on app startup and before creating a backup. After Miniflux categories/feeds are synced into the DB, `applyFeedSettingsOverridesToDB()` reapplies those local options to matching feeds only. Old backups with `feedSettings` are still accepted; restore converts those rows into `feedSettingsOverrides` instead of recreating DB feeds.
- On iOS, Secure Storage is Keychain-backed with `first_unlock` accessibility and can survive app deletion/reinstallation according to Keychain behavior. The SQLite database itself is not preserved. After reinstall, Miniflux remains the source of truth for rebuilding feeds; matching `feedSettingsOverrides` are reapplied after the first successful feed sync. Do not replace this with a restored stale feed database.
- The local-data deletion dialog offers two scopes. "Feed icons only" deletes the dedicated icon directory, clears loaded news/feed icon bytes, and rebuilds widget snapshots without touching SQLite or audio downloads; a later sync downloads missing icons again. "All data" keeps the full cleanup behavior and also cancels downloads, stops an initialized audio handler, and deletes downloaded audio, artwork, and download metadata.

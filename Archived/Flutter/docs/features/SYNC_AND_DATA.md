# Flux News Sync, Data, Configuration, and Tests

Detailed context for synchronization, SQLite integrity, configuration reads, networking, logging, and relevant automated tests.

## Background Sync

- Background sync is implemented through the Flutter `workmanager` plugin.
- Dart entrypoint: `fluxNewsBackgroundCallbackDispatcher` in `lib/functions/background_sync_service.dart`.
- Task identifier / iOS BGTaskScheduler identifier: `dev.kevincfechtel.fluxNews.backgroundSync`.
- Settings are stored under `backgroundSyncIntervalMinutes`; `0` disables the scheduled task and any value above `0` means enabled. The UI intentionally exposes only an on/off switch. When enabled, the native schedule is registered with a fixed 30 minute period to avoid promising exact 15/30/45/60 minute execution that Android/iOS cannot guarantee.
- iOS also registers the native Workmanager BGAppRefresh handler in `AppDelegate.swift` with a 30 minute reschedule interval. Older stored values like 15/45/60 are normalized to 30 on app startup or during a background run. On iOS, `configureFluxNewsBackgroundSync` only cancels an existing pending task when such a stored interval migration happens; it must not cancel on every app start because that can keep pushing the next BGTask into the future. After registration, the app logs `isScheduledByUniqueName` and `printScheduledTasks()` for diagnostics.
- The background task creates a headless `FluxNewsState`, reads secure storage through `readConfigValues()`, applies config through `applyStoredConfigValuesHeadless()`, opens SQLite, runs the Miniflux sync steps, cleans DB limits, and updates the widget snapshot.
- The background task intentionally does not initialize the audio handler, CarPlay, Android Auto, or Flutter UI.
- Podcast/audio downloads are not started in the background. If `autoDownloadAudioAfterSync` is enabled, the task stores the new audio-news IDs in secure storage and `runPendingForegroundAudioDownloads()` starts those downloads only when the app is opened normally.
- iOS uses both `BGAppRefreshTask` and `BGProcessingTask` via `workmanager_apple`; identifiers are registered in `AppDelegate.swift` and permitted in `Info.plist`. The processing task is rescheduled after execution when background sync remains enabled. Execution time and exact frequency remain system-controlled by iOS. Android uses Android WorkManager periodic work with network connectivity constraint.
- Background sync logs are intentionally diagnostic. They record when the WorkManager callback is received, unknown tasks are ignored, the in-isolate guard skips a run, the cross-isolate sync lock skips a run, config/auth/fetch steps succeed or fail, widget snapshot updates are requested, pending foreground audio downloads are marked, and final cleanup completes. Use these entries to distinguish "the OS did not start the task" from "the task started but skipped/failed inside Flux News".
- `configureFluxNewsBackgroundSync` logs a `reason` for each registration/cancel path. Current reasons include `app_config_load` when the app opens and config is loaded, and `settings_changed` when the background-sync setting is changed. Use these logs together with `Registering periodic background sync`, `Registering iOS processing background sync`, and `Scheduled background tasks` to confirm that opening the app re-registers/reactivates the requested iOS background tasks.
- Foreground app activity is tracked through `shared_preferences` key `flux_news_foreground_active_at`. The app writes a fresh timestamp on `resumed`, refreshes it every 60 seconds while foregrounded, and removes it on `inactive`/`paused`/`hidden`/`detached`. Background sync skips if the marker is younger than 2 minutes and deletes stale/invalid markers so a crash or force-kill cannot block background sync indefinitely.
- Resume behavior intentionally matches the pre-background-sync app behavior when background sync is disabled: `FluxNewsBody` only runs the deferred "treat resume as startup" sync when `syncOnStart` is enabled AND `backgroundSyncIntervalMinutes > 0`. A real cold/startup sync still follows the existing `syncOnStart` setting. Possible future option: add a separate setting for timed resume-startup sync, likely with a persisted timestamp, so users can opt into sync-on-resume even when the app stays in the app switcher and never cold-starts.
- Podcast/audio playback progress now uses `shared_preferences` through `lib/functions/audio_progress_store.dart`. The store reads SharedPreferences first, migrates legacy `flutter_secure_storage`/Keychain values on first access, and deletes migrated legacy keys. New progress writes no longer hit Secure Storage. The value `"0"` is still preserved as an explicit completed/reset marker.
- Android forces `androidx.work:work-runtime:2.11.2` because `workmanager_android 0.9.0+2` declares `2.10.2`, which has a known Android 15/16 connectivity issue. Root Gradle also pins the `home_widget` Glance artifacts to `1.1.1` for deterministic widget builds.
- Foreground sync and background sync share a file-based lease in `lib/functions/sync_lock.dart`. The lock lives in Application Support and is acquired with exclusive file creation, so it works across Dart isolates. The owner refreshes the lease timestamp once per minute; only a lease that has not been refreshed for 10 minutes can be replaced. A second foreground or background sync is skipped instead of running in parallel.
- **Mark as read on scrollover** serializes observer events and processes only newly crossed indexes. SQLite persistence remains awaited per item; successful changes update the affected row through a per-item status listenable, use stable article keys, and request serialized/latest-only widget snapshot generation. This avoids the previously unsuccessful optimistic/batched persistence experiments. Representative physical-device profiling remains required to verify input latency and identify any remaining native widget, SQLite, build, or raster bottleneck.

## Database And Sync Integrity

- Miniflux remains the source of truth for categories, feeds, and feed metadata. Local per-feed options are preserved separately through `feedSettingsOverrides` and reapplied after server data is inserted.
- Foreground and background sync treat the unread-news, category/feed, and starred-news responses as one authoritative server snapshot. News pages are written to a connection-local SQLite TEMP staging table and released from Dart memory as they arrive. Local reconciliation, cleanup, read-state changes for missing entries, and starred cleanup start only after all three requests succeeded. A failed request discards staging; never convert a transport/server failure into an authoritative empty result.
- The shared implementation for this contract is `lib/functions/sync_pipeline.dart`. `fetchRemoteSyncSnapshot()` fetches and validates main-news pages, categories/feeds, and starred-news pages in order. Capped results may merge fetched entries but are not authoritative for absence cleanup. After category/feed reconciliation succeeds, `reconcileRemoteSyncSnapshot()` applies staged news, attachments, missing-read state, and starred state in one SQLite transaction. Category/feed database changes, feed-icon files, and Secure Storage override effects remain outside that news transaction.
- Database schema version 12 creates indexes for the main date, status/date, feed/status/date, starred/date, sync-status, attachment-news, attachment-URL, and feed-category query paths. Main list queries use equality for concrete `read`/`unread` status values and omit the status predicate for "all" instead of using `LIKE '%'`, so SQLite can use those indexes. Keep index creation in `lib/database/database_schema.dart` so new installs, upgrades, and tests use the same definitions.
- Database schema version 11 adds nullable `news.previewText` and `news.imageUrl` columns. Normal sync writes both values together with the full article content. The main news-list and widget queries intentionally select an empty `content` value plus `contentLoaded = 0`; they use the stored preview/image metadata and therefore do not allocate or parse every full article while building a list. A selected/expanded article loads its full content separately through `ensureNewsContentLoaded()`. Direct single-article queries still return full content.
- `insertNewsInDB()` preserves stored `content`, `previewText`, and `imageUrl` when it receives a list-only `News` object (`contentLoaded == false`). This matters for podcast downloads: `downloadAudioAction()` persists attachment/progression data after the download, but the `News` object can come from a list query with intentionally empty content. Only fully loaded entries may refresh the stored content and derived metadata.
- `News.fromJson()` intentionally does not prepare list metadata because Miniflux JSON does not contain the local per-feed preferences yet. Insert/update paths first load `preferParagraph` and `preferAttachmentImage`, then call `prepareListMetadata()` once. Search results likewise apply all local feed settings before preparing metadata.
- `prepareListMetadata()` parses article HTML once and derives both preview text and the HTML image from that document. Image selection also considers image attachments and honors `preferAttachmentImage`. Changes to either metadata-relevant feed setting regenerate stored metadata for the affected feed; applying restored `feedSettingsOverrides` does the same when those values changed.
- The version-11 `onUpgrade` block only adds the two columns. It must not parse all existing article HTML while SQLite is opening, because that can block first startup or trigger an ANR on large databases. Missing metadata (`previewText IS NULL OR imageUrl IS NULL`) is instead backfilled after list loading in batches of 50, yielding between batches and using full feed/attachment rules. Visible rows are updated in memory when their backfill completes.
- SQLite calls `onUpgrade` once with the installed `oldVersion` and current `newVersion`. The standalone `if (oldVersion < 11)` block therefore also runs for direct upgrades from old versions such as 5 to 11. Do not copy version-11 `ALTER TABLE` statements into older migration branches; prior migrations only need to remain capable of bringing their older schemas forward before the final version-11 block runs.
- `insertCategoriesInDB()` has a global destructive-cleanup guard: when local feeds exist but the fetched Miniflux result contains zero feeds, local category/feed cleanup is skipped and a warning is logged. This protects against transient, malformed, or partially failed sync responses wiping the complete feed table and associated settings. The guard intentionally applies to the globally empty feed result; normal deletion of feeds that are genuinely absent from a non-empty Miniflux response remains allowed.
- News for a selected category are queried in one global SQL result ordered by `news.publishedAt`, independent of feed. Do not reintroduce per-feed querying/concatenation because that groups chronological results by feed.
- Dynamic feed-ID filtering uses `_buildChunkedInClause()` so categories with more than SQLite's normal bind-parameter limit remain supported. Attachment loading is also chunked in groups of 500.

## Test Coverage Notes

- Shared Flutter tests now use `test/test_helpers.dart` for an in-memory Flux News SQLite schema plus a `flutter_secure_storage` MethodChannel mock. Prefer this helper when adding DB or settings tests so schemas stay aligned and Secure Storage behavior is consistent.
- The release workflow runs `flutter analyze lib test` and the complete `flutter test` suite before signing or building release artifacts. Keep analysis scoped to app/test sources because the checked-in Flutter SDK under `vendor/flutter` is not application code.
- `test/miniflux_http_client_test.dart` covers request timeout and client cleanup. `test/sync_lock_test.dart` covers lock exclusion, release, and stale-lock replacement. `test/asset_references_test.dart` catches missing files referenced by Dart asset literals. Database integrity tests also cover schema indexes and awaited starred-news/attachment persistence.
- `test/sync_pipeline_test.dart` covers complete and genuinely empty remote snapshots, failures at each of the three fetch stages, long-sync aborts after news/categories, preservation of real SQLite rows after an incomplete snapshot, successful reconciliation of an authoritative empty snapshot, canonical reconciliation order, and stopping after an error at each local database stage. Foreground and background sync both consume this shared pipeline.
- `test/database_integrity_test.dart` covers the global empty-Miniflux-feed guard, genuine server-side feed deletion cleanup, category-level chronological ordering across feeds, feed-ID chunking above SQLite bind limits, and immediate persistence of feed settings overrides.
- `test/settings_backup_service_test.dart` covers plain backup export, encrypted backup password handling, exclusion of internal backup keys, and restore of legacy feed-settings backup data into both Secure Storage overrides and the current DB.
- `test/widget_snapshot_test.dart` verifies the Dart snapshot payload that native iOS/Android widgets consume. `FluxNewsWidgetService.buildWidgetSnapshotPayload()` is intentionally exposed with `@visibleForTesting`; native HomeWidget persistence/reload remains in `updateWidgetSnapshot()`.
- `test/background_audio_test.dart` covers the foreground-active marker decision used by background sync and the `AudioProgressStore` migration from legacy Secure Storage into SharedPreferences.
- `test/config_read_test.dart` covers successful, empty, failed, and retried Secure Storage reads so transient failures cannot become an empty configuration. `test/audio_download_cleanup_test.dart` and `test/feed_icon_cleanup_test.dart` cover the two local-data deletion scopes. `test/news_model_test.dart`, `test/news_list_query_test.dart`, and `test/miniflux_backend_test.dart` cover preview/image metadata, lightweight list loading, lazy full-content loading, and important Miniflux persistence/update paths.
- Downloaded audio protects its associated news from feed cleanup. Feed/news deletion checks protected downloaded-news IDs before removing local rows.
- Every successful foreground sync replaces the in-memory list from SQLite, sets `scrollPosition` and the persisted position to `0`, and calls `jumpToItem(0)`. This reset is intentional: retaining an old midpoint after unread rows disappear can make mark-as-read-on-scroll incorrectly mark many new rows.
- A completed background sync writes a completion timestamp. On resume, and only while background sync is enabled, the foreground compares that timestamp with `lastNewsListLoadedAt`; if newer, it reloads the list from SQLite and resets to position 0. The in-app browser remains open while the app is backgrounded; the reload occurs when Flutter actually resumes and must not dismiss the browser.
- Background task failures remain isolated to background logs and WorkManager retry status; the headless `FluxNewsState` does not publish popup state into the foreground instance. Foreground error dialogs consume a non-empty message snapshot before their asynchronous presentation and serialize concurrent errors through `errorDialogVisible`. A new foreground sync clears `errorString` and `newError` together, preventing the previous race where the scheduled dialog retained `newError == true` after its message had already been cleared and consequently opened empty.
- Mark-as-read and mark-as-unread actions update the widget snapshot. Bulk mark-as-read-on-scroll also needs to refresh the widget after database updates. The scroll observer must not mark items merely because a short, non-scrollable list changes lifecycle/viewport geometry; `allItemsVisible` prevents the bottom-of-list path in that case.

## Configuration Read Integrity

- `FluxNewsState.readConfigValues()` distinguishes a successfully read but genuinely empty Secure Storage from a read failure/timeout. On failure it returns `false`, marks `configValuesReadSuccessfully = false`, and preserves the previously loaded `storageValues`; it must never replace them with an empty map.
- Foreground startup retries a failed Secure Storage read up to three times. Migration, DB/config application, Android auto-backup refresh, widget refresh, audio-download handling, startup sync, and WorkManager configuration run only after a successful read. If every attempt fails, startup suppresses Welcome navigation and exposes the existing error state; a later foreground resume retries initialization.
- Background sync aborts the current run immediately when configuration cannot be read. It must not apply default values, write normalized settings, initialize sync from an empty configuration, or alter the existing periodic schedule. The sync lock is still released by the normal `finally` cleanup.
- `configureFluxNewsBackgroundSync()` refuses to register or cancel work unless the current `FluxNewsState` has completed a successful configuration read. This specifically prevents a transient Secure Storage failure from interpreting the default interval `0` as a user request to disable background sync.
- The Android incident on 2026-07-04 showed WorkManager and foreground Flutter engines reading Secure Storage concurrently. Both reads timed out after the process resumed, the old implementation treated them as empty settings, displayed Welcome, and cancelled WorkManager. A second app start read the intact values successfully, proving that the settings had not been deleted. Preserve the failure-vs-empty distinction in future config refactors.

## SQLite Factory Constraint

- The main mobile database must use the normal `sqflite` mobile factory. Do not add a global `databaseFactory = databaseFactoryFfi` assignment: enabling the FFI factory on Android caused startup failure because `/data/data/de.circle_dev.flux_news/lib/libsqlite3.so` was not packaged.
- Production code now imports `sqflite` directly. The narrow read-only metadata fallback in `AudioDownloadService` uses normal mobile `openDatabase(..., readOnly: true)` as well. `sqflite_common_ffi` remains a development dependency only for in-memory tests; do not import or initialize it from production code.

## HTTP And Version Metadata

- All Miniflux HTTP calls create clients through `lib/miniflux/miniflux_http_client.dart`. Android continues to use embedded Cronet without Google Play Services; other platforms use `IOClient`. Requests and response streams have a 30-second timeout, and every owned client is closed in `finally`, including early-return and error paths. Injected test clients remain caller-owned.
- The installed app version is loaded from native package metadata with `package_info_plus` during startup. Do not add a second hardcoded Dart version. The iOS Runner and Widget extension both consume `FLUTTER_BUILD_NAME` and `FLUTTER_BUILD_NUMBER`; the widget target configurations must retain their `Generated.xcconfig` base configuration or Xcode strips the extension version fields.

## Logging

- The former `flutter_logs`/PLog implementation was removed after native PLog crashes. Logging now uses the Dart `logger` package plus the app-owned file writer in `lib/functions/logging.dart`; do not restore old PLog crash workarounds unless PLog itself is reintroduced.
- Android and iOS use the same hourly filename format `ddMMyyyyHH.log`, the same 24-hour timestamp format `dd MMM yyyy HH:mm:ss`, and the same startup retention cleanup. Log date directories older than 7 days and exported log ZIPs older than 1 day are removed.
- Android writes below external app storage when available; iOS writes below Application Support. `readFluxNewsLogs()` recursively combines `.log`/`.txt` files for export.

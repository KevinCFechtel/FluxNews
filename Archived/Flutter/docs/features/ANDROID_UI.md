# Flux News Android UI

Detailed implementation context for Android floating chrome, tablet/adaptive layouts, system bars, toolbars, and related UI behavior.

## Android Floating App UI

- Status: initial implementation completed on 2026-08-09. Android General Settings now offers a fourth AppBar type, `floating` / localized `Floating`, alongside normal, collapsible, and glass. Floating chrome is the Android default whenever no persisted AppBar selection exists; an explicitly saved user selection continues to take precedence.
- The full floating title/count and configurable toolbar are applied to the Android smartphone layout. In a single-pane portrait window the actions remain in the bottom toolbar. In a single-pane landscape window the same configured toolbar automatically moves beside the title at the top-right, while the bottom action toolbar and bottom edge gradient disappear; download/audio banners may still use the bottom edge, and the final news item retains a scrollable system-navigation inset. The decision uses the current pane's `width > height`, not a physical-device label, and only applies to the floating AppBar style. Android tablets retain their permanent category/feed sidebar but no longer render a redundant full-width AppBar: a fixed branding header with the same theme-colored open-book icon used by the Drawer button and the Flux News name sits above the independently scrolling All News/Bookmarks/category/feed list, while an `AndroidFloatingToolbar` containing fixed Sync/abort and optional More actions plus the same configured direct actions floats at the top-end of the news pane. Selected direct actions are removed from the tablet More menu just as on phones, and the legacy optional FAB is not rendered on tablets. A 64px list header spacer keeps the first card below it. The complete tablet body uses all system safe areas, including the bottom gesture/three-button navigation inset, so both the feed sidebar and news pane remain scrollable above system navigation. Because `_BottomBanners` is always registered as the Scaffold's `bottomNavigationBar` even while empty, the tablet shell captures the unmodified window metrics before building the Scaffold and sets the maximum of `padding.bottom`, `viewPadding.bottom`, and `systemGestureInsets.bottom` as the bottom `SafeArea.minimum`; `maintainBottomViewPadding` remains enabled. This prevents Scaffold/edge-to-edge padding consumption from hiding the last news row behind either Android navigation mode. The tablet shell also sets the system overlay style explicitly. Expanded foldables and tablets that satisfy the existing 600px width/480px height two-pane thresholds keep this tablet structure; a folded device, shallow multi-window, or horizontal-hinge sub-screen that resolves to a single pane follows that pane's portrait/landscape rule. Tablet list inset/reset behavior is always active and must not depend on the hidden smartphone `appBarType`. The optional accent-tint and floating-action configuration settings are visible on Android tablets regardless of that type and control this toolbar. Smartphone-only news-count/AppBar-style/FAB settings are hidden on Android tablets.
- The smartphone `Scaffold` keeps the existing Drawer but omits the AppBar. A fixed top overlay now mirrors the iPhone information hierarchy: a standalone leading open-book bubble opens the Drawer, followed by one rounded translucent title surface whose width follows short title text and grows loosely only up to the available maximum; long titles retain single-line ellipsis. When the existing `multilineAppBarText` preference is enabled, the numeric count is plain text beside the title inside that same surface rather than a separate bubble. The count remains `FluxNewsCounterState.appBarNewsCount`, so its meaning continues to follow the current All/Unread filter and selected All News/bookmarks/category/feed logic. No separate unread-only count or query was added.
- `lib/ui/android_floating_chrome.dart` owns the Material/BackdropFilter surfaces. They use tightly clipped 12px blur, theme-derived translucent `surfaceContainer`, restrained elevation, a more opaque no-blur high-contrast fallback, and a black backer in True Black mode. The title surface uses the same compact 12px horizontal/6px vertical padding and 6px title/count gap as iOS. The Drawer bubble and action toolbar paint compact 40px surfaces while retaining separate 48px touch areas, so phone and tablet controls look smaller without reducing Material interaction targets. Flutter's Material 3 `IconButton` path ignores the legacy `splashRadius`; the floating toolbar therefore applies a shared 36px `ButtonStyle` state layer with 6px padding around each 24px icon. Flutter's padded tap target remains 48px, while the pressed overlay has a real 2px inset from the 40px toolbar surface on phones and tablets. Non-floating AppBars retain their normal Material state layer. The Drawer glyph and tablet sidebar brand glyph are both 24px. The Android Sync progress indicator remains at its original stable 15px extent in floating and non-floating layouts on phones and tablets. A persisted Android-only `androidFloatingAccentTint` switch (on by default and shown only for the floating AppBar type) controls whether the top Drawer/title surfaces and bottom toolbar receive tint and outline from the active `ColorScheme.primary`. The neutral base alpha is 0.72 in Light and True Black and 0.82 in regular Dark Mode; True Black therefore remains visibly translucent even when accent tint is disabled instead of appearing like an opaque black surface. High Contrast stays at 0.94. Dark Mode blends the regular base surface 22% toward black and reduces accent, border, elevation, and shadow prominence. `liquid_glass_widgets` is not used on Android.
- A scrollable initial top inset keeps the first card below the fixed header while later cards can pass behind it. The inset scales with the current text scaler. Empty/loading/error/long-sync/too-many-news bodies receive the same top accommodation through `FluxNewsBodyList`.
- The bottom floating toolbar reuses the existing Android `appBarButtons()` behavior rather than duplicating Sync/abort or More-menu commands. Like the iPhone toolbar, its fixed ordering now starts with Sync/abort; configurable direct actions follow, with More remaining last whenever it contains an unselected applicable action. The Drawer action exists only in the standalone top bubble. Sync and More remain pinned while only the configurable middle section scrolls on narrow windows. The entire Android floating-action settings tile opens a dedicated full settings page backed by the selected-action JSON list `androidFloatingToolbarActions` and the complete JSON order `androidFloatingToolbarActionOrder`; changes are saved immediately, including reordering disabled actions. Android and Apple expose the same seven configurable actions: Search, the contextual All/Unread switch, sort direction, current-scope Mark as Read, Mark as Read and Next, Podcasts, and Settings. Mark as Read and Next is rendered only for a selected feed or category. The configuration page uses stable toggle labels rather than the current command outcome, and the default Android selected list is empty. Selected direct actions are removed from More, and More disappears when all currently applicable actions are selected. Other AppBar types ignore the stored direct-action list and retain the complete applicable More menu. The configured set is never silently changed based on width. The pre-release aggregate `androidFloatingToolbarShortcuts` switch/key was removed without migration because no released build stored it. The legacy Mark-as-read FAB long-press remains intentionally available in non-floating Android layouts for established users, even though it overlaps the explicit Mark as Read and Next command.

- Adaptive shell selection is centralized in `lib/ui/adaptive_layout.dart`: two-pane mode starts at 600 logical pixels of width and requires at least 480 logical pixels of height, preventing compact-height landscape phones from receiving the tablet shell. The same policy drives the main shell, audio player, download banner, and mini player. Android tablet sidebars use a 260–360px bounded width without decorative dividers below the brand header or between the navigation and news panes. Vertical separating display features still reserve the physical hinge/fold and place navigation and news in separate sub-screens; horizontal separating features use a safe single-sub-screen smartphone presentation instead of spanning interactive UI across the hinge.
- Bottom chrome stacks the existing download banner and podcast mini-player above the floating toolbar and applies the bottom safe area only once. `Scaffold.extendBody` plus a dynamic bottom sliver spacer keeps the final news card reachable as banners appear or disappear.
- Android floating layouts use the shared, non-interactive `FloatingChromeEdgeGradient` between scrolling news and the screen edges. It intentionally uses no blur. On portrait phones, the top gradient starts 25px below the status/header chrome, while the bottom gradient starts 25px above the dynamically measured bottom chrome (floating toolbar, system navigation, and any active banners). The bottom gradient is tied directly to the presence of the bottom action toolbar: compact-landscape panes omit both and use only the top treatment behind the combined title/actions row; Android tablets likewise have only their top treatment because their actions are already at the top. The floating controls sit inside the ramp rather than on an already opaque block. At normalized stops `0, 0.16, 0.34, 0.51, 0.68, 0.84, 1`, Dark Mode keeps the user-tuned opacity curve `0%, 15%, 25%, 45%, 55%, 70%, 100%`; Light Mode uses the softer `0%, 12%, 20%, 36%, 46%, 62%, 100%` curve because a light scaffold color is visually more prominent at equal alpha. Both reach the full scaffold background only at the physical edge, and the top treatment mirrors the curve. This steadies translucent controls against high-contrast cards without hiding a larger portion of the scrolling content or blocking gestures.
- The opt-in `automaticFeedIconContrast` setting is disabled by default and appears below the global feed-icon visibility switch. When enabled, feed icons without a manual light/dark adaptation override are analyzed once at a 32px raster size and cached by icon identity plus a sampled byte fingerprint. In Dark Mode, a predominantly dark icon with meaningful transparent area receives a small light rounded contrast surface; opaque icons and already-light icons keep their original presentation. Raster and SVG sources share the same alpha-weighted luminance analysis, while the existing per-feed manual adaptation settings always take priority. An independently persisted, default-empty set of ignored feed IDs lets the user suppress automatic highlighting for individual feeds; the corresponding switch is shown in expanded feed settings only while the global automatic feature is active. This exception is a local display preference in Secure Storage, requires no database migration, survives feed synchronization, and participates in settings backups. Clearing downloaded feed icons also clears the analysis cache.
- The optional Android FAB is suppressed only while the floating style is selected because Sync is already permanently available in the toolbar and Mark as Read remains in More. FAB-specific Settings rows are hidden in this mode. Persisted FAB visibility/action values are not deleted and take effect, with their Settings rows, when another AppBar style is selected.
- News-card metadata uses the same trailing order on Android and iOS in both portrait cards and wide rows: feed title, optional playback duration, conditional bookmark/star slot, then publication date. The date is therefore always the final right-aligned item at the card content edge instead of remaining inset by the bookmark slot; the shared headline-on-top metadata follows the same order. The 40px star slot is built only for actually bookmarked news, so ordinary feed titles can consume that otherwise empty width before ellipsizing.
- Android floating mode resets index 0 to the shared scroll controller's minimum extent. This preserves the scrollable header inset after sync, menu filter/sort changes, and feed/category navigation instead of placing the first card behind the fixed title.
- The floating and collapsible/scrollover smartphone shells supply `AnnotatedRegion<SystemUiOverlayStyle>` for correct light/dark system-bar icons while their content can occupy Android's edge-to-edge status-bar region.
- A fixed `AndroidStatusBarScrim` sits above scrolling content in both floating and collapsible/scrollover Android smartphone modes. It is not added to normal or already pinned AppBar modes, avoiding stacked protection. The overlay covers the system status-bar inset plus a compact 6px fade, applies an 8px blur to detailed cards, and uses the current scaffold background at 92% opacity before fading to transparent. High contrast disables blur and raises opacity; True Black retains a black base. This implements Android's matching-background gradient-protection recommendation for non-sticky top chrome and keeps clock, connectivity, and battery icons readable behind forced edge-to-edge content. Accent tint remains reserved for the floating title, count, and bottom toolbar.
- Automated verification completed with `flutter analyze lib test`, focused adaptive/iOS-edge/Android-floating tests, and the complete Flutter test suite (105 tests). `test/adaptive_layout_test.dart` covers the shared compact-landscape decision and system-navigation inset, `test/ios_liquid_glass_style_test.dart` covers the explicit bottom-control edge-effect switch and stable Sync icon extent, and `test/android_floating_chrome_test.dart` covers the Android gradients and floating controls. Manual iPhone/Android rotation testing is still required for long localized titles, large text, active download/player banners, menu placement, and raster performance.
